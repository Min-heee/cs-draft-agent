# 실제 경로 검증: `DRAFTER=claude-code` (2026-10-21)

2차와 3차 평가는 비용을 아끼려고 Claude Code **하위 에이전트**에게 운영 프롬프트를 따르게 해서 초안을 만들었습니다. 이번에는 실제 운영 경로로 같은 16건을 돌렸습니다. 운영 경로는 검토 화면의 "새 문의 불러오기"가 쓰는 `claude -p` + MCP 서버입니다. 그리고 두 가지를 확인했습니다.

1. 실제 경로가 끝까지 동작하는가
2. 하위 에이전트 평가가 실제 경로를 제대로 대표하는가

**결론**
- 실제 경로는 두 번 모두 16건 전부 성공했습니다. API 비용은 0원입니다.
- 하위 에이전트 평가는 **실제 경로보다 후하게** 나왔습니다. 특히 정책을 찾아보는 빈도가 일관되게 달랐습니다.
- 그래서 프롬프트를 바꿨을 때 최종 판정은 실제 경로로 해야 합니다.

- **수정 후 (3회차)**: 사이즈 답변의 정책 안내가 0/4에서 4/4가 됐고, 결과 약속 표현과 앞뒤가 안 맞는 이관은 코드가 표시합니다(아래 "수정 후 확인").
- **수정 후 (4·5회차)**: 배송지 변경 정책 문장을 바꾸자 1208의 약속 표현이 3/3에서 0/2가 됐습니다. 바지 기장 안내는 이제 데이터에서 나옵니다(아래 "남은 두 가지 처리").
- **수정 후 (6·7회차)**: 합배송 정책 문장을 바꾸자 1214의 약속 표현이 3/5에서 0/2가 됐습니다. 두 실행 전체에서 결과 약속 표현은 0건입니다(아래 "합배송 정책 문장").
- **원본 데이터**
  - 실제 경로 1~7회: `data/eval-cc.db`, `data/eval-cc2.db` … `data/eval-cc7.db`
  - 사람이 읽기 좋게 뽑은 것: 같은 이름의 `.md`
  - 채점 결과: `data/eval-cc-judgments.json`

## 돌리기까지 고친 것

실제 경로를 처음 돌리면서 테스트만으로는 드러나지 않던 문제가 여섯 가지 나왔습니다. 모두 고쳤고, 코드로 고칠 수 있는 것은 테스트를 추가했습니다(테스트 73개).

| 문제 | 증상 | 조치 |
|---|---|---|
| `.env`의 API 키가 `claude`로 넘어감 | 구독으로 돌린다던 경로가 API 키로 과금될 수 있었다 | `claude`를 띄울 때 API 인증 변수를 뺀다 (`claudeEnv`) |
| 앱을 Claude Code 안에서 띄우면 그 세션 변수가 넘어감 | `claude`가 사용자 로그인 대신 부모 세션 인증을 써서 401 | `CLAUDE_CODE_*`, `ANTHROPIC_BASE_URL` 등도 뺀다 |
| 앱 설정 `CLAUDE_EFFORT`가 Claude Code 자체 변수와 겹침 | 세션 값 `xhigh`가 섞여 들어옴 | 설정 이름을 `DRAFT_MODEL`, `DRAFT_EFFORT`로 바꿈 |
| 키체인 로그인이 6월 이후 갱신 안 됨 | `auth status`는 "loggedIn"인데 실제 호출은 401 | 사용자가 `claude auth login` 다시 실행. 확인은 실제 호출로 하도록 README에 적음 |
| CLI 2.1.146은 Opus 5.5를 못 씀 | 400 "2.1.280 or newer is required" | npm으로 2.1.306 설치 |
| CLI 2.1.306이 zod 스키마의 `$schema` 키를 거부 | "not a valid JSON Schema" | `--json-schema`에서 `$schema`를 뺌 (`draftJsonSchema`) |
| CLI 내부 `StructuredOutput` 호출이 도구 기록에 섞임 | 검토 화면 "에이전트가 확인한 것"에 초안이 한 번 더 나옴 | 우리 MCP 도구만 기록 |

평가 시각을 하위 에이전트 평가와 같은 15:30으로 맞추려고 `EVAL_NOW`도 추가했습니다.

## 하위 에이전트(3차)와 비교

### 결과가 같은 것

`scripts/compare-runs.ts`로 비교했습니다.

- 문의 유형 16/16, 사이즈 계산 결과 4/4(3XL/4XL, 40/42, 38/40, 4XL/5XL)가 같았습니다.
- 첫 줄·서명 형식 16/16, 상투적 맺음말 0, 확인 필요 9건도 같았습니다.
- 답변 문장 차이는 평균 40%입니다. 참고로 실제 경로 두 번끼리도 35%, 하위 에이전트 2차와 3차끼리도 44%가 납니다. 문장 차이 대부분은 실행마다 생기는 흔들림입니다.

| 지표 | 하위 에이전트 2차 | 하위 에이전트 3차 | 실제 경로 1 | 실제 경로 2 |
|---|---|---|---|---|
| 정책 검색 횟수 | 27 | 27 | 18 | 20 |

| 사이즈 문의에서 첫 사이즈 교환 무료 안내 | 2 | 2 | **0** | **0** |

| "담당자가 확인 후 안내"인데 확인 필요 꺼짐 | 없음 | 없음 | 1209 | 없음 |

실제 경로는 **정책을 덜 찾아봅니다.** 그 결과 사이즈 답변에서 사이즈 가이드 상담 원칙이 빠집니다. 상담 원칙은 "추천은 참고용이며 첫 사이즈 교환 무료를 함께 안내"하라는 내용입니다. 실제 경로 두 번 모두 그랬습니다.

### 채점자 비교 (실제 경로 1회 vs 하위 에이전트 3차)

채점자 한 명이 문의마다 두 초안을 같은 기준으로 봤습니다. 에이전트 16개, 약 118만 토큰이 들었습니다.

| | 통과 | 경미 | 실패 |
|---|---|---|---|
| 하위 에이전트 3차 | 42 | 5 | 1 |
| 실제 경로 | 30 | 18 | 0 |

비교 판정은 나아짐 4, 같음 29, **나빠짐 15**입니다. 나빠진 내용은 위 표와 같은 방향입니다.

- **사이즈 답변의 정책 안내 누락** (1201, 1211)
- **처리 결과 약속**: 1208 "회사 주소로 변경을 진행하고", 1214 "합배송으로 처리하고"
- **앞뒤가 안 맞는 이관**: 1209는 담당자 후속 안내를 쓰고도 확인 필요가 꺼져 있음
- **근거 없는 가정**: 1206 "지금은 확정된 일정이 없어"
- **정책 밖 표현**: 1216 "더 빨리", "댓글로"

나아진 것도 있습니다.
- 1203이 하위 에이전트의 부풀린 표현("배송 진행 상황 확인")을 쓰지 않았습니다.
- 1216이 조회 안 된 주문번호를 고객 답변에서 뺐습니다.

**해석할 때 주의할 점**: 채점자 한 명의 판정은 흔들립니다. 3차 평가 때 같은 하위 에이전트 초안이 통과 37을 받았는데, 이번에는 42를 받았습니다. 그래서 위의 코드 지표(두 번 반복해도 같은 방향)를 더 믿을 만한 근거로 봅니다.

### 왜 다른가 (가설)

두 경로는 모델과 프롬프트 문장은 같지만 놓인 자리가 다릅니다.

- **하위 에이전트**: Claude Code의 기본 시스템 프롬프트 아래에서 우리 프롬프트를 파일로 **읽고** 따릅니다. 기본 시스템 프롬프트는 도구를 꼼꼼히 쓰도록 이끕니다.
- **실제 경로**: `--system-prompt`로 우리 프롬프트**만** 시스템 프롬프트로 씁니다.

게다가 우리 프롬프트는 "배송비, 기간, 교환·반품 조건 … 같은 정책은 search_policy로"라고만 하고, 사이즈 답변에서 상담 원칙을 찾아보라고는 하지 않습니다. 그 빈틈이 실제 경로에서 드러났습니다.

## 수정 후 확인 (실제 경로 3회)

아래 수정 1~3을 코드에 넣고 실제 경로로 16건을 한 번 더 돌렸습니다. 16건 모두 성공했고 78초가 걸렸습니다. 이번에는 채점자 없이 코드 지표로만 확인했습니다. 프롬프트는 바꾸지 않았습니다.

1. **`recommend_size` 결과에 상담 원칙을 함께 돌려줌**: "추천은 참고용"과 첫 사이즈 교환 무료 정책 문장을 섹션 ID와 함께 `안내_원칙`으로 넣습니다. 모델이 정책을 따로 검색하지 않아도 사이즈 답변을 쓸 때 늘 보게 됩니다.
2. **코드 규칙: 처리 결과를 약속하는 표현 감지**: "변경을 진행하고", "합배송으로 처리하고", "접수해 두었습니다" 같은 표현이 있으면 `[자동] 처리 결과를 약속하는 표현이 있음("…")`을 붙입니다. "처리해 드립니다"처럼 정책을 일반적으로 설명하는 현재형은 잡지 않습니다.
3. **코드 규칙: 담당자 후속 안내를 약속했는데 확인 필요가 꺼져 있으면 켬**

| 실행 | 도구 호출(정책 검색) | 사이즈 문의 정책 근거 | 사이즈 답변 첫 교환 무료 안내 | 결과 약속 표현 | 담당자 안내인데 확인 필요 꺼짐 | 확인 필요 |
|---|---|---|---|---|---|---|
| 하위 에이전트 3차 | 50 (27) | 3/4 | 2/4 | 1210 | - | 9 |
| 실제 경로 1 | 40 (18) | 1/4 | 0/4 | 1214, 1208 | 1209 | 10 |
| 실제 경로 2 | 43 (20) | 1/4 | 0/4 | 1214, 1208 | - | 9 |
| **실제 경로 3 (수정 후)** | 41 (19) | **4/4** | **4/4** | 1208 → 자동 표시됨 | 1209 → 확인 필요 켜짐 | 9 |

"결과 약속 표현"과 "확인 필요 꺼짐" 열은 모든 실행에 현재 코드 규칙을 다시 적용해서 셌습니다.

- **수정 1 (사이즈 안내)**: 사이즈 문의 4건 모두 계산 결과대로 추천했습니다(3XL/4XL, 40/42, 38/40, 4XL/5XL). 네 건 모두 "추천은 참고용"과 첫 사이즈 교환 무료 신청 방법을 안내하고, 근거에 `size-guide#상담 원칙`과 `exchange-return#첫 사이즈 교환 무료`를 적었습니다. 내부 메모에는 에이전트가 직접 "첫 교환 무료 사용 이력 확인"을 적었습니다. 정책 검색 횟수(19회)는 그대로인데 결과가 바뀐 것이니, 검색에 기대지 않고 도구 결과로 보장하는 방식이 효과가 있었습니다.
- **수정 2 (결과 약속)**: 모델은 1208에서 또 "변경을 진행하고"라고 썼습니다. 하지만 이번에는 초안을 만들 때 코드 규칙이 표시해서, 검토 화면의 노란 상자에 그 문구가 그대로 나옵니다. 프롬프트로는 없어지지 않던 표현을 승인 전에 반드시 보게 만든 것입니다.
- **수정 3 (확인 필요 보정)**: 1209는 이번에도 담당자 후속 안내를 쓰고 확인 필요를 껐습니다. 이제 코드가 확인 필요를 켜고 이유를 남깁니다.
- **유지된 것**: 형식 규칙 16/16, 본문 7문장 초과 0건, 확인 필요 9건. 평균 길이는 정책 안내가 붙어 302자에서 333자로 늘었습니다.

**오탐 확인**: 두 규칙을 지금까지의 초안 80건(1·2·3차, 실제 경로 1·2회)에 다시 적용했습니다. 걸린 8건(1208, 1209, 1210, 1214)은 모두 처리를 약속하는 문장이거나 앞뒤가 안 맞는 이관이었고, 오탐은 없었습니다. 지표용 정규식이 놓쳤던 "합배송을 진행하고"(실제 경로 2회 1214)도 잡았습니다.

## 평가 방법

프롬프트를 바꿀 때 빠른 반복은 하위 에이전트로 하고, 최종 판정은 실제 경로로 합니다.
- 실제 경로 초안 생성은 `DRAFTER=claude-code EVAL_NOW=…`로 80초 안팎, 약 25만 토큰입니다.
- 코드 지표는 `scripts/compare-runs.ts`로 봅니다.
- 품질 채점이 필요하면 `eval/workflow.js`의 `judgeOnly`로 합니다(16개 에이전트, 약 118만 토큰).

## 남은 두 가지 처리 (실제 경로 4·5회)

3회차 뒤에 남았던 두 가지를 고치고 실제 경로로 16건을 두 번 더 돌렸습니다. 두 번 모두 16건 성공했고 각각 80초, 98초 걸렸습니다.

1. **배송지 변경 정책 문장**: "변경은 마이페이지에서 직접 하시거나, CS팀이 본인 확인 후 처리합니다"를 "변경은 마이페이지에서 직접 하실 수 있습니다. 게시판으로 변경을 요청하시면 CS팀이 본인 확인 후 **처리 여부를 안내**합니다"로 바꿨습니다(`data/policies/shipping.md`).
2. **바지 기장 안내를 데이터로 제공**
   - 실측표에 "기본 기장이 수선 없이 맞는 키 범위"(`length_fit_height`)를 넣었습니다. 슬랙스는 175~182cm, 데님은 174~181cm로, MD가 정하는 값입니다.
   - 사이즈 계산이 고객 키와 비교한 결과를 `lengthNote`로 돌려줍니다. 예: "키 170cm는 기본 기장이 수선 없이 맞는 키(175~182cm)보다 작아 총장 106cm가 길 수 있음".
   - `get_product`도 이 범위를 보여 줍니다.

| 실행 | 1208 결과 약속 표현 | 1208 답변의 담당자 문장 |
|---|---|---|
| 실제 경로 1~3 (옛 정책 문장) | 3회 모두 "변경을 진행하고" | 3회 모두 옛 정책 문장 "CS팀이 본인 확인을 거친 뒤 처리해 드립니다"를 옮겨 씀 |
| 실제 경로 4 | **없음** | "CS팀이 본인 확인을 한 뒤 처리 여부를 안내드리겠습니다" |
| 실제 경로 5 | **없음** | "CS팀이 본인 확인을 한 뒤 처리할 수 있는지 다시 안내해 드리겠습니다" |

| 실행 | 1202 사이즈 계산 결과의 기장 안내 | 1202 답변의 기장 문장 |
|---|---|---|

## 합배송 정책 문장 (실제 경로 6·7회)

합배송 정책도 같은 방식으로 바꿨습니다(`data/policies/shipping.md`). 바꾸기 전에는 "CS팀이 확인해 처리합니다. 이미 낸 배송비는 합배송 후 환불합니다"였고, 지금은 "CS팀이 확인해 **합배송 가능 여부를 안내**합니다. 합배송으로 보내게 되면 이미 낸 배송비는 환불합니다"입니다. 실제 경로로 16건을 두 번 돌렸고, 두 번 모두 16건 성공에 각각 78초가 걸렸습니다.

| 실행 | 합배송 정책 문장 | 1214 결과 약속 표현 | 1214 답변의 담당자 문장 |
|---|---|---|---|
| 1 | 옛 문장 | "합배송으로 처리하고" | "…확인한 뒤 합배송으로 처리하고, 처리 결과를 안내해 드리겠습니다" |
| 2 | 옛 문장 | "합배송을 진행하고" | "…확인한 뒤 합배송을 진행하고, 결과를 이 글에 안내해 드리겠습니다" |
| 3 | 옛 문장 | 없음 | "…확인한 뒤 합배송 진행 여부를 … 안내해 드리겠습니다" |
| 4 | 옛 문장 | "합배송으로 처리하고" | "…확인한 뒤 합배송으로 처리하고 결과를 안내해 드리겠습니다" |
| 5 | 옛 문장 | 없음 | "…확인한 뒤 합배송 가능 여부를 안내해 드리겠습니다" |
| **6** | **새 문장** | **없음** | "…확인한 뒤 합배송 가능 여부를 이 글에 답변으로 안내해 드리겠습니다" |
| **7** | **새 문장** | **없음** | "…확인한 뒤 합배송 가능 여부를 이 게시글로 안내해 드리겠습니다" |

- **1214**: 약속 표현이 옛 문장일 때 3/5에서 새 문장일 때 0/2가 됐습니다.
- **1208**: 정책을 바꾼 뒤 네 번 모두 약속 표현이 없었습니다.
- **두 실행 전체**: 결과 약속 표현은 0건입니다. 표본이 두 번뿐이라 "없어졌다"고 단정할 수는 없습니다. 다만 모델이 정책 문장을 그대로 옮겨 쓴다는 점이 1208과 1214에서 같은 방식으로 확인됐습니다. 그래도 나오면 코드 규칙이 표시합니다.

**앞서 고친 것은 유지됐습니다.**

| 실행 | 사이즈 문의 정책 근거 | 사이즈 답변 첫 교환 무료 | 1202 기장 안내 | 결과 약속 표현 | 꼭 확인할 7건 누락 | 형식 |
|---|---|---|---|---|---|---|
| 6 | 4/4 | 4/4 | 데이터 근거 | - | 없음 | 16/16 |
| 7 | 4/4 | 4/4 | 데이터 근거 | - | 없음 | 16/16 |

확인 필요가 7건보다 많은 것은 모두 코드 규칙이 설계대로 표시한 건입니다.
- 1204: 계산한 신청 마감일 10/23
- 1203: 6회차에 도착 예상일 10/22를 적음
- 1209: 6회차에 담당자 후속 안내를 썼는데 확인 필요가 꺼져 있음

### 다음 후보

- **정책 문장 점검**: 정책 문장이 모델의 표현을 그대로 끌고 간다는 것이 두 번 확인됐습니다. "처리합니다", "해 드립니다"처럼 결과를 단정하는 다른 정책 문장도 한 번에 찾아 점검하는 것이 좋습니다. 예를 들어 불량·오배송 정책의 "무료 교환이나 반품을 안내합니다"는 이미 "안내" 형태라 괜찮습니다.

진행 결과는 [정책 문장 점검](POLICY-AUDIT.md)에 있습니다(실제 경로 8~11회).
