# 불만 사유 리포트

카페24에 쌓인 고객 글(상품 후기, 상품 Q&A, 댓글)을 매일 아침 읽어, 상품마다 **무엇 때문에 불만인지** 순위로 보여 줍니다. CS 답변 초안과 같은 앱 안에 있고, 관리자 화면의 '불만 사유' 탭과 `data/reports/`의 HTML·CSV·엑셀로 봅니다.

- 결재 20261027-M-1-1 A(반품·불만 사유 리포트). 계획: `.office/reports/20261028-1514-빅레그-1.md`
- **읽기만 합니다.** 카페24에는 GET만 하고, 쇼핑몰에 아무것도 쓰지 않습니다.
- LLM은 로그인한 Claude Code(구독)로만 부릅니다. API 키(유료) 경로는 쓰지 않습니다.

## 흐름

```
카페24 (GET만)          분류                                    리포트
 상품 후기  ─┐     ① 규칙: 낱말·별점으로 후보          ┌─ 지난 7일·30일 순위(지난 기간 대비)
 상품 Q&A   ─┼─▶   ② Claude: 사유·부위·근거 구절 ─▶ 저장 ─┼─ 상품별 순위 + 대표 인용(개인정보 가림)
 댓글       ─┘     ③ 코드 검사: 근거가 원문에 있나,     ├─ '늘어난 사유' 알림(관리자 화면)
 (우리 답글·직원 글 뺌)  확신도, 별점, 글 속 지시        └─ data/reports/complaints-날짜.html·csv·xlsx
```

- **GET 전용 읽기**: `Cafe24ApiClient.readOnly()`가 GET만 하는 함수를 돌려주고, 리포트 코드(`src/complaints/`)는 이것만 받습니다. 앱 토큰에는 게시판 쓰기 권한도 있지만 리포트 쪽에서는 쓰기 함수에 닿을 수 없습니다.
- **고객 글만 셉니다**: 답이 달렸는지와 상관없이 고객 원글과 댓글을 모두 읽습니다. 답글(`parent_article_no`)과 직원 이름(`CAFE24_REPLY_WRITER`, `CAFE24_STAFF_WRITERS`)의 글·댓글은 뺍니다. 목록은 100건씩 끝까지 나눠 읽습니다.
- **한 번만 분류**: 글마다 본문 해시로 결과를 저장하고, 새 글과 바뀐 글만 Claude에 보냅니다. 매일 다시 분류하지 않으니 순위가 날마다 흔들리지 않습니다.
- **배치**: 글 10건을 한 번에 보냅니다. 글 키 대신 `p1, p2…`를 넘겨 키가 모델에 새지 않게 합니다. 도구는 모두 끄고(`--tools ""`) MCP도 붙이지 않습니다.
- **확인 필요**: 근거 구절이 원문에 없음, 확신도 낮음, 별점 1~2인데 사유 없음, 글 속에 분류를 바꾸라는 지시가 있음. 이런 글은 순위에는 세고 대표 인용에서는 빼며, 화면의 '확인 필요 글' 목록에서 이유와 함께 봅니다.
- **주입 지시**: 지시가 보이는 글은 한 건씩 따로 보내 같은 묶음의 다른 글에 번지지 않게 합니다. 규칙이 못 본 지시를 Claude가 찾으면 같은 묶음 글에도 확인 필요를 붙입니다.
- **Claude 실패**: 로그인 만료·시간 초과 등으로 분류에 실패한 글은 규칙 결과로 세고 '대신 채움'으로 표시합니다. 화면에 경고가 뜨고, 다음에 만들 때 다시 분류합니다.
- **범위**: 출처(카페24·목업·시험 파일)마다 따로, 마지막 실행에서 본 글만 셉니다. 카페24에서 지운 글은 빠집니다. 리포트 파일·관리자 화면·알림이 같은 범위를 씁니다.
- **늘어난 사유**: 지난 7일 건수가 3건 이상이고 그 앞 7일보다 늘었을 때만 알립니다. 그 앞 7일에 글이 하나도 없으면(가게를 막 연 첫 주, 한꺼번에 올린 시연 자료) 견줄 기준이 없어 알리지 않습니다. 같은 날 다시 만들어도 같은 알림은 한 번만 남깁니다(건수가 늘면 다시).
- **매일 아침**: 10분마다 "오늘 것을 만들 때가 됐나"(한국 시각 9시 이후, 오늘 아직 안 만듦)를 봅니다. 9시에 앱이 꺼져 있었으면 켠 뒤 처음 확인할 때 만듭니다. 앱을 14일 넘게 끄면 카페24 리프레시 토큰이 끝나 다시 동의해야 합니다.
- **개인정보**: 리포트에는 이름·아이디를 넣지 않고 DB에도 작성자 이름을 저장하지 않습니다. 인용문의 전화번호(+82·띄어쓰기 포함)·주문번호·주민번호·이메일·계좌번호·긴 숫자·주소(도로명·동호)와, "입금자명·받는 분·주문자·카톡 아이디·@아이디"처럼 이름표가 붙은 이름·아이디는 가립니다(`src/complaints/mask.ts`). 이름표 없이 본문에 그냥 쓴 이름은 가리지 못합니다. 카페24 본문(HTML)은 글자로 바꾼 뒤 다룹니다. 리포트 파일과 시험 글은 git에 올리지 않는 폴더(`data/reports/`, `data/complaint-eval/`)에만 둡니다.

## 실행

```bash
npm run complaints
```

지금 설정(`CAFE24_MODE`, `COMPLAINT_CLASSIFIER`)대로 한 번 만들고 `data/reports/complaints-날짜.html·csv·xlsx`를 씁니다. 관리자 화면(`npm start`)에서는 '불만 사유' 탭이 매일 9시 이후 자동으로 만들고, '지금 만들기' 버튼으로도 만듭니다. 화면의 순위는 저장된 분류 결과로 다시 셀 뿐, Claude나 카페24를 부르지 않습니다.

| 설정 | 뜻 |
|---|---|
| `COMPLAINT_CLASSIFIER` | `rules`(규칙만) 또는 `claude-code`(규칙 + Claude Code 구독). 비우면 `DRAFTER=claude-code`일 때 claude-code |
| `COMPLAINT_REPORT_HOUR` | 매일 몇 시(한국 시각) 이후 만들지. `off`면 자동으로 만들지 않음 |
| `COMPLAINT_SOURCE` | 시험 글 파일로 만들어 볼 때(예: `data/complaint-eval/dev.json`). 출처별로 따로 세므로 정식 리포트·알림·'오늘 만듦' 기록과 섞이지 않고, 파일 이름에 출처가 붙습니다 |

## 엑셀과 구글시트

### 엑셀 (지금 됨)

리포트를 만들 때마다 `data/reports/complaints-날짜.xlsx`도 씁니다. 관리자 화면의 '엑셀 받기'는 고른 기간(7일·30일·전체)으로 바로 만들어 줍니다. 패키지를 더하지 않고 `src/complaints/xlsx.ts`가 직접 만듭니다.

| 시트 | 내용 |
|---|---|
| 요약 | 기간별 고객 글, 불만 글, 불만 아님, 확인 필요, 대신 채움 |
| 사유 순위 | 기간·순위·사유·건수·불만 글 중 비율(%)·지난 기간 건수 |
| 상품별 | 상품마다 사유와 건수, 상품 불만 글 중 비율 |
| 글별 분류 | 글마다 작성 시각(한국, 날짜 형식)·종류·상품·별점·사유·확인 필요와 이유·짧은 인용. 매일 파일은 지난 30일, 화면에서 받을 때는 고른 기간 |
| 정보 | 기준 시각, 자료 출처(시연 자료면 그렇다고 적음), 분류 방식, 만든 시각, 안내 문장 |

- 제목 줄은 굵게 고정하고 필터를 걸어 두었습니다. '글별 분류'에서 '확인 필요=예'나 사유로 바로 거를 수 있습니다.
- 작성자 이름은 넣지 않습니다. 인용은 리포트와 같이 짧게(Claude가 고른 근거 구절, 없으면 앞 90자) 가려서 넣고, 불만도 확인 필요도 아닌 글은 인용을 비웁니다.
- 글자는 글자로만 넣습니다(수식을 쓰지 않음). "=…"로 시작하는 고객 글은 열 때도, 셀을 고쳐 Enter를 눌러도 계산되지 않게 글자로 고정합니다.
- 구글 드라이브에 이 파일을 올리면 구글시트로 열 수 있습니다.

### 구글시트 자동 연결 (대표님 준비가 필요)

앱이 대표님 구글 계정의 시트에 매일 직접 쓰려면, 앱이 쓸 수 있는 열쇠(서비스 계정 키)가 필요합니다. 대표님이 하실 일은 이렇습니다.

1. [Google Cloud 콘솔](https://console.cloud.google.com/)에서 프로젝트를 만들고 'Google Sheets API'를 켭니다.
2. 'IAM 및 관리자 → 서비스 계정'에서 서비스 계정을 만들고, 키(JSON)를 받아 **저장소 밖**에 둡니다.
3. 구글시트를 하나 만들고, 서비스 계정 메일 주소(…@….iam.gserviceaccount.com)에 **편집자**로 공유합니다.
4. `.env`에 키 파일 경로와 시트 ID(주소의 `/d/`와 `/edit` 사이)를 직접 적습니다. 키 내용은 채팅에 붙이지 않습니다.

그다음 빅레그 창에서 "구글시트 준비했어"라고 말씀하시면, 같은 네 시트를 그 시트에 덮어쓰는 코드를 붙입니다.

## 정확도 (2026-10-28)

```bash
npm run eval:complaints -- --runs 3 --sets dev,holdout,hard
```

'규칙만'과 '규칙+Claude+코드 검사'를 같은 글로 비교했습니다. Claude는 구독 경로(claude-opus-5-5, effort medium), 배치 10건·동시 3배치로 각각 세 번 돌렸습니다.

최종 코드로 돌린 결과입니다(`data/complaint-eval/results-2026-10-28T07-09-30.md`, git에는 올리지 않음).

| 시험 글 | 글 수 | 규칙만 맞힘 | 규칙만: 확인 필요 없이 틀림 | 규칙+Claude 맞힘 (세 번) | 규칙+Claude: 확인 필요 없이 틀림 | 규칙+Claude: 확인 필요 | 한 번 도는 시간 |
|---|---|---|---|---|---|---|---|
| 개발용(규칙·프롬프트를 만들며 본 bh044 가짜 글) | 27 | 25 (93%) | 1 | 27 · 27 · 27 | 0 · 0 · 0 | 2 | 12~13초 |
| 시험용(한 번도 보지 않은 글) | 72 | 46 (64%) | 23 | 72 · 72 · 72 | 0 · 0 · 0 | 3 | 31~33초 |
| 어려운 시험용(반어·돌려 말하기·구매 전후 혼동) | 40 | 13 (33%) | 23 | 40 · 40 · 40 | 0 · 0 · 0 | 4 | 30~40초 |

- 바로 앞의 같은 평가(검토 반영 중간 코드)에서는 시험용 한 회차가 71/72였습니다. 불만 글 하나를 확인 필요 없이 '불만 아님'으로 놓쳤습니다. 회차마다 흔들림이 있습니다.
- 대신 채운 글(Claude 실패)은 모든 회차에서 0건이었습니다.

- **맞힘**: 글의 사유 묶음이 정답과 똑같은 글 수(사이즈 부위까지 같아도 결과는 같았습니다).
- **확인 필요 없이 틀림**: 틀렸는데 '확인 필요'도 안 붙은 글. 사람이 못 보고 지나갈 수 있는 오류라 따로 셉니다.
- **규칙만의 약점**: 색상 차이(F1 0.29), 기타 불만(0.00), 배송 지연(0.73)을 많이 놓쳤습니다. 어려운 글에서는 배송 지연·색상·기타가 0.00이었습니다. 반어("2주 만에 왔네요 빠르네요")와 낱말 없는 불만을 낱말 규칙으로는 잡지 못합니다.
- **토큰**: 글 한 건에 입력 약 520~620, 출력 약 80~170토큰(구독이라 실제로 나간 돈은 없습니다).

### 이 숫자를 그대로 믿으면 안 되는 이유

- **시험 글을 Claude가 쓰고, 정답도 Claude가 달고, 분류도 Claude가 했습니다.**
  - 시험용 72건과 어려운 시험용 40건은 하위 에이전트가 기준표에 맞춰 쓴 글입니다.
  - 서로 격리한 라벨러 둘이 따로 단 정답이 작성자의 의도와 100% 같았습니다(72/72, 40/40). '어려운' 글에서도 애매한 글이 0건이었습니다.
  - 같은 모델 계열은 해석이 같아서, 이 자료로는 실제 고객 글의 어려움을 잴 수 없습니다. 100%는 '기준표대로 쓴 글은 기준표대로 나눈다'는 뜻에 가깝습니다.
- **실제 고객 글로 다시 재야 합니다.** bh044에는 실제 고객이 없습니다. 실제 쇼핑몰 글을 사람이 라벨링한 정답 세트가 있어야 진짜 정확도가 나옵니다.
- **효과(반품률·불만 감소)는 재지 않았습니다.** 상위 사유를 고친 뒤(예: 실측표 보강) 그 사유와 반품률이 줄었는지는 실제 운영에서만 잴 수 있습니다.
- **사람이 손으로 정리하는 시간은 재지 않았습니다.** 그래서 '절감 시간'은 쓰지 않습니다.
