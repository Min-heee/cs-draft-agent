> 아래 3차 수정안 1~4는 반영했습니다. 결과는 [3차 평가](EVAL-3.md)에 있습니다.

[1차 평가](EVAL-1.md)의 수정안 1~6을 반영하고 데모 문의 16건을 다시 돌렸습니다.

- **결과 요약**: 채점 48건 중 실패가 21건에서 1건으로 줄었습니다. 1차보다 나빠진 판정은 0건입니다.
- **원본 데이터**:
  - 초안: `data/eval-2-drafts.json`, `data/eval-2.db`
  - 사람이 읽기 좋게 뽑은 것: `data/eval-2.md`

## 어떻게 돌렸나: API 비용 0원

API 크레딧이 없어 Claude Code 구독으로 돌렸습니다.

- **초안 작성**: 문의마다 하위 에이전트 하나가 초안을 썼습니다. 모델은 1차와 같은 Claude Opus 5.5, effort medium입니다.
- **도구**: 에이전트는 이 프로젝트의 MCP 서버를 `scripts/mcp-call.ts`로 불러 실제 도구를 썼습니다. 1차와 같은 코드입니다.
- **입력**: 시스템 프롬프트, MCP 서버가 내주는 도구 목록(입력 스키마와 설명 포함), 출력 스키마를 실제 `claude -p` 경로와 똑같이 줬습니다(`scripts/eval-inputs.ts`).
- **채점**: 서로 독립된 채점 에이전트 셋이 각자 한 가지 기준으로 1차 초안과 2차 초안을 비교했습니다.
  - 근거·사실: 정책 문서 5개를 직접 읽고, 필요하면 도구를 다시 불러 사실을 확인
  - 안전·담당자 판단
  - 지침·문체
- **비용**: 에이전트 64개를 썼고 API 비용은 0원입니다. 구독 사용량은 약 440만 토큰이었고, 대부분이 채점에 들었습니다.
- **재현**: [eval/workflow.js](../eval/workflow.js)에 실행 방법이 있습니다.

**1차와 다른 점**: 1차는 API 도구 실행기, 2차는 Claude Code 하네스에서 돌았습니다. 시스템 프롬프트가 들어가는 위치와 도구를 부르는 방식이 다르므로 완전히 같은 조건은 아닙니다. 그래서 아래 비교는 "같은 모델, 같은 도구, 바뀐 프롬프트"의 근사치로 봐야 합니다.

### 평가 환경 자체의 버그를 먼저 고쳤습니다

첫 시도에서는 하위 에이전트에게 도구 이름과 간단한 예시만 주고 입력 스키마를 주지 않았습니다. 출력 스키마에도 필드 설명을 빼먹었습니다. 그 결과가 이랬습니다.

- 1201·1211에서 "평소 3XL", "어깨 넓음", "허벅지 굵음"을 사이즈 계산에 넘기지 못해 대안 사이즈가 빠졌습니다. 채점자는 이걸 프롬프트 탓의 퇴보로 판정했습니다.
- 16건 중 13건이 `sources`를 정해진 형식이 아닌 자유 문장으로 썼습니다.

실제 경로와 똑같은 도구 목록과 출력 스키마를 주도록 고친 뒤 다시 돌렸습니다. 아래 결과는 고친 평가 환경 기준입니다. 고친 뒤에는 1201·1211 모두 체형 정보를 빠짐없이 넘겼고, `sources` 형식도 16건 모두 맞았습니다.

**덤으로 찾은 실제 약점**: 직원 모드 `save_draft`의 "다른 회원의 주문" 검사가 `sources`의 `order:` 형식에만 의존하고 있었습니다. 첫 시도처럼 모델이 `get_order:…`로 쓰면 검사를 그냥 지나칩니다. 이제는 근거, 답변, 내부 메모 어디에 나온 주문번호든 모두 확인합니다. 테스트도 추가했습니다.

## 남은 문제와 3차 수정안

### 프롬프트

1. **정책보다 부풀린 기능·경로** (1203 주요, 1208·1213·1216 경미)
   - 사례: "마이페이지 > 주문내역에서 송장번호로 **실시간 배송 위치**를 확인", "**가장 빠른 방법**은 …", "댓글로 남기면 **더 빠르게** 확인".
   - 정책 문장에 없는 기능, 비교, 속도 주장입니다.
   - 수정안: "정책 문장에 없는 기능이나 세부 동작(실시간 조회, 메뉴 위치, '가장 빠른 방법' 같은 비교, 처리 속도)을 덧붙이지 않고, 정책 문장의 범위 안에서만 바꿔 씁니다."
2. **"담당자가 확인한 뒤 안내드리겠습니다"가 너무 막연해짐** (1208, 1210)
   - 1차의 "지어낸 절차"를 막으려고 넣은 표준 문구가 모든 이관 건에 쓰였습니다.
   - 그래서 담당자가 **무엇을** 확인하는지가 빠졌습니다. 예: 1210에서 "이전 문의가 왜 처리되지 않았는지 확인하겠다"는 접수 안내가 사라짐.
   - 수정안: "담당자에게 넘길 때는 담당자가 확인할 내용을 구체적으로 적되, 결과는 약속하지 않습니다."
3. **내부 메모가 얇아짐** (1201, 1213, 1214)
   - 빠진 것: 첫 교환 무료 사용 이력 확인, "공개 게시판에 사업자번호 쓰지 않기" 안내, "물류팀에 출고 보류 요청" 같은 구체적인 지시.
   - 수정안: "internal_note에는 담당자가 할 일을 순서대로 적습니다(누가, 무엇을, 언제까지). 고객 답변에 쓴 조건 중 자격 확인이 필요한 것(첫 교환 무료 등)도 적습니다."
4. **고객이 실제로 걱정하는 점을 놓침** (1203 "주말에 입어야 해요", 1202 "너무 길지 않을까요?")
   - 날짜를 약속하지 말라는 규칙을 지키다 보니 질문에 직접 답하지 않습니다.
   - 수정안: "약속은 하지 않되, 고객이 말한 사정(주말 등)에 비춰 정책 기간이 어떤 의미인지는 말해 줍니다."

### 코드 (이번에 반영)
