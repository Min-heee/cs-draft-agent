# CS 문의 답변 초안 에이전트

개인 프로젝트입니다. 쇼핑몰·고객·주문·글·정책 자료는 모두 가상입니다. 카페24 테스트 쇼핑몰(bh044)에 연결해, 승인한 Q&A 답글 1건과 후기 댓글 1건을 실제로 등록했습니다([실제 카페24 연결](docs/LIVE-BH044.md)). 실제 고객이나 CS 직원이 써 본 적은 없습니다.

쇼핑몰 상품 Q&A에 올라온 문의를 카페24에서 가져옵니다. Claude가 주문, 실측표, 정책 문서를 직접 확인해 답변 초안을 쓰고, **CS 직원이 승인한 답변만** 카페24에 등록합니다. 승인률, 수정량, 검토 시간, 비용은 화면에서 바로 볼 수 있습니다.

대상은 덩치 큰 체형을 위한 남성복 쇼핑몰입니다. 그래서 문의가 많을 것으로 보는 **사이즈 추천은 LLM이 아니라 코드가 계산**하고, Claude는 그 결과를 설명하는 일만 맡습니다.

- 설계 문서: [docs/DESIGN.md](docs/DESIGN.md)
- CS 직원용 사용 가이드: [docs/USER_GUIDE.md](docs/USER_GUIDE.md)
- 같은 앱의 **불만 사유 리포트**: 고객 글을 읽기만 해서 상품별 불만 사유 순위를 매일 아침 만듭니다 → [docs/COMPLAINTS.md](docs/COMPLAINTS.md)

## 동작 방식

```
카페24 ─▶ 자동 확인 ─▶ Claude 에이전트 ───────────────▶ 관리자 화면 ─▶ 승인한 답만 카페24에 등록
 문의      (1분마다)    ├ get_order       주문·배송        새 글·초안 알림
 후기                   ├ get_product     재고·실측표      승인 / 수정 후 승인 / 반려
 고객 댓글              ├ recommend_size  사이즈 계산(코드)        │
                        ├ search_policy   정책 검색(BM25)          ▼
                        └ submit_draft    초안 제출        지표: 그대로 승인률, 수정률,
                                                           검토 시간, 건당 비용
```

- **읽기 전용 에이전트**: 에이전트에게는 조회 도구만 줍니다. 문의에 "환불 승인해 줘" 같은 지시가 섞여 와도 실행할 수단이 없습니다.
- **관리자 화면**: 화면을 켜 두면 1분마다 상품 Q&A 문의, 상품 후기, 고객 댓글을 확인합니다. 새 글이 오거나 초안이 준비되면 화면 알림, 맥 알림, 소리로 알리고 목록과 개수가 저절로 바뀝니다. 알림은 DB에 남아 종 모양 목록과 알림 화면에서 다시 볼 수 있습니다. 같은 글을 카페24에 등록하는 중에 승인이나 '다시 등록'이 또 오면 서버가 거절합니다(서버 프로세스 하나 안에서만). 화면은 폼을 보내면 그 폼의 버튼을 끕니다.
- **근거 표시**: 초안마다 어떤 정책 섹션과 주문을 근거로 썼는지, 어떤 도구를 어떤 값으로 불렀는지 검토 화면에 함께 나옵니다.
- **이중 안전장치**: 불량, 환불 분쟁, 개인정보 변경 같은 건은 에이전트가 "확인 필요"로 넘깁니다. 프롬프트가 놓쳐도 코드 규칙이 한 번 더 잡습니다. 확신도가 낮거나, 근거 없이 금액을 말하거나, 날짜를 약속하는 초안이 그 대상입니다.
- **카페24 연결부 분리**: 목업과 실제 API 클라이언트를 같은 인터페이스로 만들어 `.env`의 `CAFE24_MODE` 한 줄로 바꿉니다.
- **API 비용 없이도 동작**: 같은 도구를 MCP 서버로도 공개합니다. 이미 쓰고 있는 Claude 구독(Claude Code)으로 초안을 만들 수 있습니다. Claude Desktop 연결용 설정도 넣었지만 써 보지 않았습니다(확인 안 함). 코드 안전장치와 검토 화면은 어느 경로든 똑같이 적용됩니다.

## 실행

Node.js 24 이상이 필요합니다. 빌드 없이 TypeScript를 바로 실행합니다.

```bash
npm install
```

### 키 없이 둘러보기

API 키, Claude, 카페24, 구글시트 없이 관리자 화면을 봅니다. `.env`는 읽지 않습니다.

```bash
npm run start:demo
```

다른 포트로 띄우려면 `PORT=3100 npm run start:demo`로 실행합니다. 하는 일은 넷입니다.

1. `data/demo.db`를 지우고 처음부터 만듭니다. 그래서 다시 실행하면 앞에서 승인·반려한 것이 사라지고 같은 화면에서 시작합니다.
2. 3차 평가 때 Claude가 쓴 초안 16건(`data/eval-3-drafts.json`, 목업 상품 Q&A 1201~1216)을 `scripts/import-drafts.ts`로 넣습니다. 모델 이름은 `claude-code-subagent:claude-opus-5-5`로 나옵니다. 3차 평가(Claude Code 하위 에이전트, 정책 문장 점검 전 프롬프트·정책)의 초안이라, 그 뒤 고친 동작(첫 교환 무료 자격 확인 문구, 접수 확정 금지 등)은 반영되지 않았습니다. 코드 안전장치는 넣을 때 지금 규칙으로 다시 적용합니다.
3. 불만 사유 리포트를 규칙만으로 한 번 만듭니다. Claude는 부르지 않습니다. 파일은 `data/reports/complaints-2026-10-21.*`에 쓰고, 실행할 때마다 덮어씁니다.
4. 관리자 화면을 띄웁니다(http://localhost:3000).

데모 설정은 `DRAFTER=fake`, `COMPLAINT_CLASSIFIER=rules`, 자동 확인 꺼짐(`AUTO_SYNC_SECONDS=0`)입니다.
- 처음 화면은 문의함 검토 대기 7건, 확인 필요 9건이고, 가짜 초안은 없습니다.
- 불만 사유 탭(지난 7일·30일·전체)은 목업 고객 글 30건으로 채워집니다.
- 후기 11건과 고객 댓글 3건은 기록된 초안이 없어 처음에는 들어 있지 않습니다. **지금 확인**을 누르면 들어오고 가짜 초안이 붙습니다. 초안에서 **다시 만들기**를 눌러도 가짜 초안으로 바뀝니다.
- 승인해도 목업에만 기록되고 실제 카페24에는 올라가지 않습니다.

### Claude API로 실행

```bash
cp .env.example .env
```

`.env`의 `ANTHROPIC_API_KEY`에 Claude API 키를 넣고 실행합니다.

```bash
npm start
```

http://localhost:3000 을 열면 관리자 화면이 뜨고, 데모 문의 16건·후기 11건·고객 댓글 3건을 불러와 초안을 만들기 시작합니다. 그 뒤로는 1분마다(`AUTO_SYNC_SECONDS`) 새 글을 확인합니다. 오른쪽 위 **지금 확인**으로 바로 확인할 수도 있습니다.

알림이 한 건씩 오는 모습을 목업으로 보려면 확인할 때마다 글을 조금씩 내놓게 합니다.

```bash
MOCK_DRIP=1 AUTO_SYNC_SECONDS=10 npm run start:fake
```

`.env`를 쓰되 API 키 없이 화면만 보려면 가짜 초안 모드로 실행합니다. 초안에 "테스트용 가짜 초안" 표시가 붙습니다.

```bash
npm run start:fake
```

**목업 기준 시각.** 카페24 목업 모드(`CAFE24_MODE=mock`, 기본)에서 `EVAL_NOW`가 없으면 앱의 '지금'은 2026-10-21 15:30(한국 시각)입니다. 목업 글 날짜에 맞춘 값입니다(`src/config.ts`의 `MOCK_NOW`).
- 이 시각을 쓰는 곳: `npm start`, `start:fake`, `start:claude-code`, `draft`, `complaints`, `scripts/import-drafts.ts`(오늘 시각을 안 줄 때), MCP 서버(`src/mcp/main.ts`). `scripts/eval-inputs.ts`도 오늘 시각을 안 주면 `MOCK_NOW`를 씁니다.
- 바뀌는 것: 초안 프롬프트의 오늘 날짜, 날짜 안전장치, 불만 사유 기간과 리포트 파일 날짜. 매일 리포트는 이 날짜로 한 번만 만듭니다.
- 실제 카페24 모드(`CAFE24_MODE=api`)는 실제 시각을 씁니다. 목업 모드라도 `COMPLAINT_SOURCE`로 시험 글 파일을 읽으면 실제 시각을 씁니다.
- 서버를 켜면 '기준 시각: …' 줄이 찍힙니다.

### API 비용 없이 쓰기 (Claude 구독)

초안을 만드는 방법은 세 가지이고, 어느 쪽이든 검토 화면, 안전장치, 지표는 같습니다.

| 방법 | 비용 | 쓰는 곳 |
|---|---|---|
| `DRAFTER=claude` | API 크레딧 | 운영. 문의가 들어오면 서버가 바로 초안을 만든다 |
| Claude Desktop + MCP 서버 | 구독에 포함 | CS 직원이 "새 문의 초안 써 줘"로 한 번에 처리(연결은 확인 안 함) |
| `DRAFTER=claude-code` | 구독에 포함 | 개발·데모. 관리자 화면이 새 글을 가져오면 `claude -p`로 초안을 만든다 |

**Claude Desktop에 연결하기.** 아래 연결은 아직 Claude Desktop에서 써 보지 않았습니다(확인 안 함). 같은 MCP 서버의 문의 한 건 모드는 Claude Code 경로(`claude -p`)에서 실제로 썼고, Desktop이 쓰는 직원 모드는 테스트로만 확인했습니다. 설정 > 개발자 > 구성 편집에서 `claude_desktop_config.json`에 아래를 넣고 앱을 다시 켭니다. 경로는 실제 위치로 바꿉니다. Desktop 앱은 PATH를 모를 수 있으니 node는 절대 경로로 씁니다.

```json
{
  "mcpServers": {
    "cs-draft-agent": {
      "command": "/opt/homebrew/bin/node",
      "args": [
        "--env-file-if-exists=/절대경로/cs-draft-agent/.env",
        "/절대경로/cs-draft-agent/src/mcp/main.ts"
      ]
    }
  }
}
```

새 대화에서 + 메뉴의 **새 문의 초안 쓰기** 프롬프트를 고르면 Claude가 처리합니다. 새 문의를 하나씩 읽고, 주문·실측·정책을 확인한 뒤 `save_draft`로 문의함에 저장합니다. 저장한 초안은 `npm start`로 띄운 검토 화면의 검토 대기·확인 필요 탭에 나옵니다. 직원 모드의 `get_order`는 문의 초안을 쓸 때도 회원 제한 없이 조회합니다. 대신 `save_draft`가 근거로 쓴 주문이 그 문의 작성자의 주문인지 다시 확인하고, 아니면 "확인 필요"로 넘깁니다. 회원 ID가 비어 있는 주문(비회원 주문)도 작성자의 것인지 확인할 수 없어 "확인 필요"로 넘깁니다. 비회원 문의는 초안에 주문번호가 나오면 "[자동] 비회원 문의라 근거로 쓴 주문이 작성자의 것인지 확인할 수 없음(…)"을 붙입니다. 초안에 주문번호가 없어도 문의 쪽(제목, 본문, 연결 주문번호, 댓글의 앞선 글)에 주문번호가 있으면 "[자동] 비회원 문의에 주문번호가 있음(…)"을 붙입니다. 주문번호만 빼고 배송 상태나 송장을 쓴 초안도 걸러 내려는 것입니다.

**Claude Code로 초안 만들기.** 터미널에서 `claude`를 한 번 실행해 로그인해 둔 뒤 실행합니다.

```bash
npm run start:claude-code
```

문의 한 건마다 `claude -p`가 뜹니다. 이때 파일·셸 같은 기본 도구는 모두 끄고, 그 문의 작성자 범위로 묶인 MCP 읽기 도구 4개만 허용합니다. 초안은 JSON 스키마로 받습니다.

**비회원 문의의 주문 조회.** 문의 한 건의 초안을 만들 때(`DRAFTER=claude`의 도구, `DRAFTER=claude-code`의 MCP 문의 한 건 모드) 작성자가 비회원이면 `get_order`가 주문을 보여 주지 않습니다. 주문번호만 알면 남의 주문을 볼 수 있기 때문입니다. 대신 "비회원 문의라 작성자와 주문을 맞춰 볼 수 없습니다. 주문 내용을 답변에 쓰지 말고 담당자 확인으로 넘기세요." 오류를 돌려줍니다.
- 회원 문의라도 회원 ID가 비어 있는 주문(비회원 주문)은 같은 까닭으로 보여 주지 않습니다. 그 회원이 로그인하지 않고 산 주문일 수도 있지만 맞춰 볼 방법이 없습니다.
- 모델이 이 오류를 받고도 확인 필요를 끄고 초안을 내면, 저장하기 전에 코드가 도구 기록을 보고 "[자동] 주문 조회가 거절됨(…)"을 붙여 확인 필요로 넘깁니다. 실제 Claude가 이 오류를 받고 어떻게 쓰는지, `claude -p` 출력에 이 오류 문구가 그대로 남는지는 확인하지 않았습니다(확인 안 함).
- 목업 후기 11건은 회원 ID가 없어 여기에 해당합니다.
- bh044에 API로 올린 글은 회원과 연결되지 않습니다([실제 카페24 연결](docs/LIVE-BH044.md)). 그래서 그 몰에서는 문의 초안의 주문 조회가 모두 이렇게 거절될 것으로 봅니다. 이 변경 뒤 bh044에서 돌려 보지는 않았습니다(확인 안 함).
- MCP 실행 파일은 `CS_SCOPE=inquiry`에 `CS_MEMBER_ID`가 비어 있으면 비회원 문의로 봅니다. 범위 변수 없이 띄운 직원 모드는 회원 제한 없이 조회합니다.

로그인됐는지는 `claude auth status`가 아니라 실제 호출로 확인합니다. `auth status`는 저장된 토큰이 만료돼도 "loggedIn: true"로 나옵니다.

```bash
claude -p "ok"
```

앱이 `claude`를 띄울 때는 두 종류의 환경 변수를 빼고 넘깁니다.
- `ANTHROPIC_API_KEY` 등 API 인증 변수: `.env`의 API 키로 과금되지 않고 구독으로만 호출되게 하려는 것입니다.
- 앱을 Claude Code 안에서 실행했을 때 따라 들어오는 그 세션의 변수: 그대로 넘기면 사용자 로그인 대신 부모 세션의 인증을 쓰려다 401이 납니다.

모델과 effort 설정 이름은 `DRAFT_MODEL`, `DRAFT_EFFORT`입니다. 예전 이름 `CLAUDE_EFFORT`는 Claude Code 자체 변수와 겹쳐서 바꿨습니다.

Claude Code CLI 2.1.280 이상이 필요합니다. 그보다 낮은 버전은 Opus 5.5를 쓸 수 없다는 오류를 냅니다.

실제 CLI 2.1.306으로 16건을 돌린 결과는 이렇습니다.
- 16건 모두 성공했습니다. 동시 3건으로 73초, 건당 평균 12.8초가 걸렸고 API 비용은 0원입니다.
- MCP 서버 연결, 모델에게 보이는 도구가 4개뿐인 것, 권한 모드 `dontAsk`를 확인했습니다.
- 하위 에이전트 평가(3차)와 비교한 내용은 [실제 경로 검증](docs/EVAL-CC.md)에 있습니다.

MCP 도구는 터미널에서도 바로 불러 볼 수 있습니다.

```bash
node scripts/mcp-call.ts --member demo_user01 get_order '{"order_id":"20261020-0000123"}'
```

### 실제 Claude로 평가

데모 문의 16건을 별도 DB에서 돌리고, 결과를 마크다운으로 뽑아 아래 기대 동작 표와 대조합니다. API 크레딧이 없으면 [eval/workflow.js](eval/workflow.js)로 Claude Code 구독을 써서 돌립니다. 이 방법은 초안 작성과 채점 에이전트 셋의 비교까지 해 주고, 2차 평가가 이 방법으로 돌았습니다.

```bash
DB_FILE=data/eval.db npm run sync
```

```bash
DB_FILE=data/eval.db npm run draft
```

```bash
DB_FILE=data/eval.db npm run export > data/eval.md
```

- 평가 기록
  - [1차](docs/EVAL-1.md): API, $0.61
  - [2차](docs/EVAL-2.md): 구독 사용, 채점자 셋. 채점 48건 중 실패 21건 → 1건
  - [3차](docs/EVAL-3.md): 구독 사용, 채점자 하나로 사용량 절반. 실패 0건. 다만 같은 초안을 [실제 경로 검증](docs/EVAL-CC.md) 때 다시 채점하자 실패 1건(1203 근거)이 나왔습니다. 채점자 한 명의 판정은 흔들립니다.
  - API를 쓰지 않은 2·3차는 API 비용이 0원입니다.
  - [실제 경로 검증](docs/EVAL-CC.md): `DRAFTER=claude-code`로 열아홉 번, 매번 16건 모두 성공(1~7회는 EVAL-CC, 8~19회는 [정책 문장 점검](docs/POLICY-AUDIT.md)에 기록)
    - 하위 에이전트 평가가 실제 경로보다 후하게 나온다는 것을 확인했습니다. 실제 경로는 정책을 덜 찾아봤습니다.
    - 코드와 데이터로 보장하도록 고친 뒤, 사이즈 답변에서 교환 정책(첫 사이즈 교환 무료)을 안내한 답변이 4건 중 0건에서 4건 중 4건이 됐습니다(단위는 답변 건수).
    - 정책 문장을 "처리합니다"에서 "처리 여부를 안내합니다"로 고친 뒤에는 결과 약속 표현이 줄었습니다. 배송지 변경은 3/3에서 0/4, 합배송은 3/5에서 0/2입니다.
  - [정책 문장 점검](docs/POLICY-AUDIT.md): 정책 72문장에서 결과를 단정하는 14문장을 고쳤습니다. 조건 없이 결과를 약속한 문장이 크게 줄었습니다.
    - 첫 교환 무료를 자격 확인 없이 약속한 문장: 실행마다 5~6개에서 0개
    - 합배송 환불 금액 단정: 5/5에서 0/2
    - 검수 조건 없는 환불: 4/5에서 0/2
    - "고치면 좋은 것" 4문장도 반영했습니다. 탐침 문의에서 예약 판매 출고일을 확정한 답변이 2/2에서 0/2가 됐고, 재입고 알림을 CS가 직접 알리는 말투가 14/14에서 0/2가 됐습니다.
    - 게시판 글도 교환·반품 신청으로 인정하고, 접수 여부는 CS팀이 확인한 뒤 안내하도록 정했습니다. 1204·1210 답변 4건이 모두 게시판 글을 신청으로 다뤘고, 접수를 확정한 1건은 코드 규칙이 표시합니다.
    - 코드 규칙을 보강해 "이 글도 신청으로 접수되며" 같은 수동형 접수 확정과, 공개 게시판에 사업자등록번호·성함 같은 개인정보를 남기라는 요청도 잡습니다. 지난 초안 268건의 후보 문장 134개를 하위 에이전트가 따로 분류해 규칙과 대조했고, 엇갈린 문장은 없었습니다. 누락은 "접수"·개인정보 낱말이 든 문장 안에서만 봤습니다. 후보 문장을 분류한 기준이 규칙 설계와 같아서, 규칙이 그 기준대로 구현됐는지를 확인한 것입니다.
    - 같은 두 가지를 프롬프트에서도 막았습니다. 고친 뒤 실제 경로 14~19회 6회 중 접수 확정은 0회였습니다. 고치기 전에는 1~13회 중 11회였고, 게시판 신청 정책을 넣은 뒤(10~13회)만 보면 4회 중 3회였습니다. 그 뒤 송장번호와 사진을 보낼 곳까지 빼는 부작용이 생겨서, "주문번호·송장번호·사진은 개인정보가 아니다"를 덧붙여 바로잡았습니다(두 번 모두 복원).
    - 고객이 이미 신청했다는데 주문에 기록이 없을 때 "신청 내역이 없다"고 말하던 1210의 버릇(17회 중 9회)도 프롬프트로 막았습니다. 실제 경로 2/2와 탐침 6/6에서 고객에게 말하지 않고 내부 메모에만 적었습니다.
    - 담당자 후속 안내 규칙이 "CS팀이 … 다시 안내해 드리겠습니다"도 잡습니다. 정책이 정한 보통 절차(접수 여부, 첫 교환 적용 여부)는 빼서, 지난 초안 388건에서 새로 켜진 것은 놓쳤던 1건뿐입니다. 모델이 확인 필요를 끈 초안에서 담당자·CS팀이 확인·안내·연락한다고 쓴 문장 74개를 하위 에이전트가 따로 분류해 규칙과 대조했고, 엇갈린 문장은 없었습니다. 이것도 후보 문장을 분류한 기준이 규칙 설계와 같아서, 규칙이 그 기준대로 구현됐는지를 확인한 것입니다.

## 실제 카페24 연결

테스트 쇼핑몰(bh044)에 연결해 문의·후기 불러오기, 상품 조회, 초안 생성, 답글과 후기 댓글 등록까지 확인했습니다. 주문 조회는 없는 주문번호의 응답만 확인했고, 고객 댓글 불러오기는 API 응답 모양만 확인했습니다(확인 안 함: 실제 주문·고객 댓글). 결과와 실제 API에서 드러난 차이는 [실제 카페24 연결](docs/LIVE-BH044.md)에 있습니다. 고객 댓글 아래에 다는 댓글(`parent_comment_no`)은 아직 실제로 등록해 보지 않았습니다.

`src/cafe24/api.ts`는 카페24 Admin API 문서(2026-09-01 버전)를 보고 작성하고, bh044에서 다르게 온 응답에 맞춰 고쳤습니다. 새 쇼핑몰에 연결하는 순서는 다음과 같습니다(`scripts/cafe24-auth.ts`가 3~5번을 돕습니다).

1. 카페24 개발자센터에 가입하면 테스트용 무료몰이 생깁니다. 상품 Q&A 게시판이 있는 한국어 쇼핑몰이어야 합니다.
2. 개발자센터에서 앱을 만들고 권한을 켭니다: `mall.read_community`, `mall.write_community`, `mall.read_order`, `mall.read_product`.
3. 앱 설정의 테스트 실행으로 무료몰에 앱을 설치하고, OAuth 인증 코드로 토큰을 받습니다.
4. 받은 토큰 응답(`access_token`, `expires_at`, `refresh_token`, `refresh_token_expires_at`)을 `data/cafe24-token.json`에 저장합니다.
   - 액세스 토큰은 2시간, 리프레시 토큰은 14일 유효합니다.
   - 리프레시 토큰은 한 번만 쓸 수 있습니다. 앱이 갱신할 때마다 새 값을 이 파일에 저장합니다.
5. `GET /api/v2/admin/boards`로 상품 Q&A 게시판 번호를 확인합니다(`board_type` 5).
6. `.env`에 `CAFE24_MODE=api`, 몰 ID, 클라이언트 ID·시크릿, 게시판 번호를 넣습니다.

연결한 뒤 확인할 것:

- 답변을 답글(`reply_article_no`)로 달지, 댓글로 달지는 게시판 설정에 따라 다를 수 있습니다.
- 답글을 등록해도 원글의 `reply_status`가 바뀌지 않을 수 있습니다. bh044에서는 API로 답글을 단 뒤에도 null 그대로였습니다. 그래서 같은 목록 안에 답글이 달린 원글은 답한 것으로 봅니다([실제 카페24 연결](docs/LIVE-BH044.md)).
- 실측표가 카페24 상품 정보(`size_guide`, `additional_information`)에 있다면 `data/size-charts.json` 대신 그쪽에서 읽도록 바꿀 수 있습니다.

## 불만 사유 리포트

같은 고객 글(상품 후기, Q&A, 댓글)로 **상품마다 무엇 때문에 불만인지** 매일 아침 순위를 만듭니다. 카페24에는 GET만 하고 쇼핑몰에는 쓰지 않습니다. 관리자 화면의 '불만 사유' 탭과 `data/reports/`의 HTML·CSV·엑셀로 봅니다. 엑셀에는 요약·사유 순위·상품별·글별 분류 시트가 있고, 서비스 계정 키를 넣으면 같은 탭을 구글시트에도 씁니다.

```bash
npm run complaints
```

- Claude(구독, 도구 없음)가 사유·부위·근거 구절을 고르면, 코드가 근거가 원문에 있는지·확신도·글 속 지시를 보고 '확인 필요'를 붙입니다. 낱말 규칙은 지시를 찾고, Claude가 실패할 때 대신 채웁니다.
- 규칙만으로는 시험 글 72건 중 46건(64%)을 맞혔습니다(AI가 만든 시험 글과 AI가 단 정답 기준). 규칙+Claude 결과는 정답을 단 모델과 같은 계열이 분류해 일치도에 가까우므로 정확도 숫자로 쓰지 않습니다. 실제 고객 글 정확도는 아직 모릅니다. 자세한 숫자와 단서는 [docs/COMPLAINTS.md](docs/COMPLAINTS.md)에 있습니다.
- bh044에서 GET만으로 고객 글 27건을 읽어 33초에 리포트를 만들었습니다.
